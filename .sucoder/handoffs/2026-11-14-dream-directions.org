* What the runs showed

- Convergence :: Every LSMS_Library =--explore= run chose cache freshness, and the two after the search fix took the same five steps.
  The explorer never sees memory, so each run starts from nothing (issue 93).
- Erosion :: Run 5 selected less of =caching.md= than run 3 and deleted correct statements, because each generation is checked only against its own evidence (issue 94).
- Staleness :: Run 6 recorded two facts from a November 4 session that are no longer true: that =.gitnexus/run.cjs= is missing, and that the Python 3.9 decision is still open (comment on issue 94).
- Seeds help, on one run :: Run 6's random seed gave a new topic and the essay's core move, testing a note against a transcript; with the default 8 turns it would have stopped before reading the note (comment on issue 93).
- Recovery is fragile :: An identity mismatch rejected run 4 without naming the role or field, and the documented =--attempt 2= recovery could not run after the job's 900-second wall clock ran out (issue 95).
- Corrections reach nobody :: The two documentation errors went to ligon/LSMS_Library#1719 and ligon/LSMS_Library#1720 only because they were filed by hand (issue 92).

Measured against [[https://www.anthropic.com/research/components-of-agent-memory][the essay]] and [[https://platform.claude.com/cookbook/managed-agents-cma-dreaming-with-a-dynamic-workflow][the cookbook]], neither source randomizes.
The essay directs dreaming at a goal and at "information that's likely to change"; the cookbook reads every finished transcript since its last run.
We are tighter than both in evidence bandwidth and in preservation, and only we review before publishing.
The comparison table is in the comment on issue 93.

* Proposed order of work

1. Recovery and small fixes (issues 95, 96, 97) :: An identity error that names the role, field and trace; =--job= accepting an id; a retry that can state a new, bounded time allowance; a config-file fallback; an =flock= probe on =log_dir=.
   These are small, need no model change, and make unattended runs and experiments recoverable.
2. Seeds and leads (issue 93) :: A seed frozen in the job at preparation, tried in order: an open item from memory, then a file or note changed since the memory's last base commit, then a random file or session window.
   The memory index and open items go into the explorer's navigation.
   Version it per job, as =navigation_version= is, so earlier jobs replay.
3. Preservation and staleness (issue 94) :: Choose among keeping receipt-backed claims, re-reading their sources, or a mechanical removal check.
   Date lessons drawn from sessions, and check claims about project state against the launch commit.
4. Corrections to issues (issue 92) :: S1, the exporter, needs no model change and can start at any time.
   S2, correction tasks in a new editorial contract, is best done after 2 and 3: the same tasks serve as issues and as leads.
5. An evaluation protocol :: Each run so far is one observation.
   Before tuning briefs, fix a small protocol: a few runs per configuration (default, against seeded with a wider allowance), recording topic, path, outcome and a hand check of each claim as correct, stale or wrong.
   Write each batch up under =docs/dream/runs/=, as [[file:../../docs/dream/runs/sucoder-e1.org][the E1 report]] does; the six runs above have no report yet.
6. Savio (issues 91, 98) :: Decide where dreams over Savio work should run.
   Savio's nodes lack Landlock, and their transcripts live in the Savio home.
   Until then, =--explore= over a vantage checkout is the only working route, and its memory reaches the Savio coordinators only by hand.
7. The charter's deferred items :: The staleness pass, an organizer and pruning pass, Codex session discovery (S3b), and a scheduler example.
