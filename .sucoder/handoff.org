* A. Snapshot identity and restore gate (closes 19, re-scopes 16)

1. Snapshots write =refs/sucoder/wip-job/<token>/<job>=, a *sibling*
   namespace. Not =refs/sucoder/wip/<token>/<job>=: an existing
   =refs/sucoder/wip/<token>= blocks it with a directory/file conflict, and
   =--atomic= does not rescue delete-plus-create, so nesting costs a window
   in which the mirror holds no snapshot. Verified on git 2.43.7.
2. Restore reads *both* shapes. Among candidates whose =wip^ = HEAD=, take
   this job's own ref if one exists, else the newest whose job =squeue= says
   is not RUNNING. A failed =squeue= is unknown state, not "gone" (ledger 3):
   decline. A ref whose job id cannot be determined: decline, with a
   diagnostic. Name the source job in the restore line.
3. Refuse at config load when two configured mirrors sanitize to the same
   token, naming both. This covers 16's whole residue at once: the shared
   warn file, the staged =job-<token>.sh= / =local-tier-<token>.sh=, and the
   tmux session *and socket* (=mirror.py:213-222=), which 16 does not name
   and which fails first.
4. The shared =$CACHE_DIR/slurm-deadline-<token>.warn= still collides when
   one mirror has two live jobs. Note that =STATE_DIR= is reassigned to
   node-local =/tmp/.../$node-$JOB= in =timer_lifecycle.py:20=, so the
   node-local warn file is *already* per-job; only the =$CACHE_DIR= copy in
   shared =$HOME= collides, and the WORKSPACE prelude
   (=mirror.py:5373-5375=) is what tells the agent to poll it.

Deliberately deferred: issue 19's option 3 (warn or refuse at launch when a
mirror already holds a live job). It is a launch-flow change with an
interactive confirmation, and A.1/A.2 remove the data-loss teeth without it.
Decide it separately.

* B. Retention (closes 14)

At prepare time, never per snapshot. Drop job refs whose jobs =squeue=
reports gone, retire the legacy =refs/sucoder/wip/<token>= only once a job
ref exists, then gc the mirror with an *explicit* expiry. Never
=--prune=now=: the mirror is the human's push target on Lustre and a
snapshot may be in flight. Note that a default =git gc --prune= is a no-op
here -- =gc.pruneExpire= is =2.weeks.ago= -- which is why issue 14's first
listed option does not work.

Also document, where =wip_snapshot_minutes= is documented, that a
snapshotted repo's outputs belong in =.gitignore=.

B in progress, scoped down from the plan above on review. *No automated
=git gc= on the shared mirror.* The measured number does not support it:
LSMS_Library carries 10.51 MiB unreachable against 841 MiB packed, and
=gc --auto= would not fire there anyway (2429 loose objects against a 6700
threshold). A gc step would take a lock on the human's Lustre repository at
every launch and do nothing on the observed workload. Instead: prune the
refs, and let the =gc --auto= that =receive-pack= already runs on every hook
push collect what that makes unreachable, on the mirror's own
=gc.pruneExpire=. That turns issue 14's unbounded growth into a bound of one
expiry window of churn, and the expiry stays the human's setting -- documented,
not written by us.

If a workload later justifies an explicit gc, it should arrive as opt-in
configuration (=slurm.wip_gc=), with the =README.org= and
=config.example.yaml= updates =CLAUDE.md= requires.
