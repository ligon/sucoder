* Next phase: Slice 2

Replication, generations and restore, per the revision section of the design:

1. A watcher in the runner follows each rollout under =home/sessions= by file growth and appends new bytes with =fsync= to =DURABLE/runs/<run>/rollouts/<thread-id>.jsonl=, recording offsets in =replica.json= and the replica age in =status.json=; never in Codex's path.
2. Database generations through the SQLite backup API, captured only after every replica is confirmed byte-identical to its local file; the manifest records each thread's =next_rollout_byte_offset= (from =thread_history_projection_state=) and the replica length.
3. Restore as generation plus replicas placed at the same relative paths and rebound, refusing any generation whose recorded offset exceeds the replica; sealed means a backup after the owned server stopped.
4. Before an unattended =thread/resume=, refuse when =goals_1= holds an active goal or =queue_1= holds rows for the thread.
5. The timer's checkpoint requests, =RemoteSession= metadata and renewal integration are Slice 3; do not start them in Slice 2.

Use =fc_jevons= for normal-priority burst jobs; =co_carleton= is preemptible.
