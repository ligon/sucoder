#+TITLE: An always-on control plane: VPS as launcher and canonical host
#+DATE: 2026-10-29
#+AUTHOR: Sue
#+STATUS: Built 2026-10-30 as vantage; measurement week in progress

* Problem

The laptop is the control plane for every remote agent session: it holds the canonical repositories, the warm SSH ControlMasters to Savio, the =~/.sucoder/sessions/= records, and the tmux windows through which the human watches four or more sessions at once.
It is not always on.
Each sleep or network change kills the gateway mux, and each wake costs a certificate or OTP plus one =sucoder attach= per session.
The laptop's root filesystem is also full: 125 of 128 GiB used, 1.3 GiB free on 2026-10-29, down from 1.6 GiB on 2026-10-20 and 161 MiB on 2026-10-23 (the Savio transition handoff, =AggregationWithLimitedCommitment/.sucoder/handoff-2026-10-23-savio-transition.org= in the mirror tree).

Three decisions are tangled in "move the control center off the laptop", and only the first removes the re-authentication churn:

1. Where the control plane lives: the muxes, the launcher, the attach windows.
2. Where canonical lives.
   SuCoder's launch model pushes the launcher's canonical to the mirror (=MirrorManager._sync_remote=), so the launcher must hold canonical unless the sync model changes; issue 66 records what goes wrong when it does not.
3. How attention is paid to N sessions.
   Moving the control plane does not reduce the window cycling; it removes the OTP between cycles.

* Decision

A small virtual private server with a static public IP becomes both the launcher and the canonical host.
The laptop becomes a client: it keeps full or partial clones for editing, pushes to the VPS, and reaches the VPS's tmux over =mosh=, which survives sleep and roaming.
Savio keeps the mirrors, the allocations and the agent tmux sessions exactly as today.
GitHub, rsync.net and Bitbucket remain the downstream publication and backup remotes they are now.
One repository, =AggregationWithLimitedCommitment=, keeps its canonical on Savio scratch because its integration gate needs the formal archives and compute; the VPS holds a follower clone of that gate for launching.

Decision 3 is deferred.
The first measure is =sucoder sessions= in a =watch= window on the VPS; the next is an agent-side status push; a coordinator session that owns the others waits on the dispatch path becoming reliable (issue 79).

* Evidence

** What kills a mux, and what the certificate changed

The pre-certificate design (=d9f95e3=, 2026-03-16) and the current one are the same mechanism: one =ssh -fN -o ControlMaster=yes= to the gateway, authenticated once with PIN and OTP, with every later command multiplexed over the socket (=sucoder/tunnel.py:205=).
June made =ControlPersist= and the keepalive pair configurable with longer defaults (=3bcdbcd=).
The certificate work (=31d7747= through =795cf8e=) changed how a dead mux is re-warmed, from an OTP to a 12-hour certificate the MSM CA caps at that lifetime (=sucoder/cert.py=); it did not change how long a mux lives.

A mux dies for two reasons the FAQ names ([[file:connection-faq.org][connection FAQ, "Do tunnels survive a laptop suspend"]]): the server or a stateful firewall drops the TCP connection during a long suspend, or the client's IP changes.
Neither applies to a VPS with a static IP that never sleeps.
What remains is BRC's server-side policy, gateway maintenance, and a network stall longer than the keepalive budget (=30 s x 120 = 1 h=), which can be raised on a host that never sleeps.
BRC's ceiling is not recorded anywhere in this repository; measuring it is the first task after provisioning.

BRC's =sshd= sets =MaxSessions 1= (=sucoder/tunnel.py:131=, measured 2026-09-20).
The gateway mux therefore carries only =-W= forwarding channels, and each login-node mux is its own connection authenticated by public key through that forward.
Only the gateway hop ever needs the OTP; everything behind it re-warms without one while the gateway's single TCP connection lives.

** What SuCoder assumes about canonical

- Non-bare :: =_configure_agent_remote= (=sucoder/mirror.py:7610=) skips remote setup when canonical has no =.git= directory, and issue 66 records that =_pull_from_url= (=sucoder/mirror.py:1388=) resets the launching checkout's working tree.
  The VPS canonicals are therefore ordinary checkouts, as the laptop's are.
  A bare canonical would need =pull= taught to update refs instead; that is hours, not a redesign, and is not required for this plan.
- One launcher per remote target :: a mirror's session record lives on the host that launched it (=~/.sucoder/sessions/<mirror>--<target>.yaml=), and =sucoder sessions= flags a job no local record points at as =! no session record= ([[file:../README.org][README, "Listing your sessions"]]).
  Once the VPS launches a mirror's Savio session, the laptop must not.
- Sync policy :: =sync_policy: external= exists for a launcher that is not the authority, but issue 66 shows =--no-sync= and dry-run can still mutate Git state.
  With canonical on the VPS this policy is needed only for the ALC follower, and the fix is no longer on the critical path.

                      |                                   |-W-> dtn.brc.berkeley.edu

#+end_example

- =ligon= on the VPS :: the canonical checkouts, =~/.sucoder/config.yaml=, the =pass= store, the SSH keys and the BRC certificate, the warm muxes, the session records, and a tmux server holding one attach window per live session.
  The keeper described in [[file:tunnel-keep.org][tunnel keep]] runs here.
- =coder= on the VPS :: local mirrors under =mirror_root= for work that needs no allocation: editing, documentation, small test runs.
  This is the ordinary local SuCoder model and removes those sessions from Savio altogether.
  Memory, not disk, bounds how many run at once.
- cron :: =mirror-sync --pull= / =--push= on a schedule against the downstream remotes; =sucoder sessions --json= on a schedule into a status file; the keeper's lifetime log.
  None of these could run on the laptop.
- The laptop :: =mosh= into the VPS's tmux.
  Clones of the VPS canonicals for editing, full or partial; the ALC laptop clone is already a =blob:none= partial clone with =gate= and =inbox= remotes on Savio, and the hook obstacle recorded in the partial-clone plan (=AggregationWithLimitedCommitment/.sucoder/plan-2026-10-20-laptop-partial-clone.org= in the mirror tree) applies to any repository whose pre-commit hook reads omitted blobs.

* Sizing and placement

- Disk :: 13 GB of canonicals, about double if =coder= keeps local mirrors of the same repositories, plus the OS, Node, Python environments and history growth.
  80 GB is comfortable to start, and on EC2 the number is not a commitment: an EBS volume grows in place while the instance runs, up to 16 TB for =gp3= at 0.08 per GB-month, and the filesystem is extended online with =growpart= and =resize2fs=.
  A volume never shrinks, and each accepts one resize per six hours.
  Keep the operating system on the root volume and everything that grows on a second volume mounted at =/home=, so the data grows and is snapshotted on its own terms; cold archives belong on rsync.net or S3, not on HDD-class EBS, whose throughput tiers suit streaming and not git's small random reads.
  This is the dimension where the laptop's fixed 128 GB loses outright.
- Memory :: 4 GB runs the control plane and one local agent session; 8 GB runs two or three.
  A Claude Code or Codex session is bounded by API round trips, not bandwidth or CPU; a faster uplink does not make it faster.
- CPU :: two virtual cores, arm64.
  The laptop is =aarch64=, so a Graviton instance changes nothing about the toolchain; see the install step below.
- Region :: us-west.
  Every keystroke in an attached session now round-trips laptop, VPS, gateway, login node and compute node, so the VPS hop should add single-digit milliseconds.
- Address :: a static public IPv4, allocated 2026-10-30 as 32.184.189.233.
  This is the property that removes NAT expiry as a cause of mux death.
- Provider :: AWS EC2 on Graviton in =us-west-2=, in the =ligon-research= account under Berkeley's bCloud AWS Central Organization; DigitalOcean SFO3 is the fallback.
  The =hhsurveys= target already runs on a droplet, so a second droplet would be the least new surface; the AWS account is already billed, settles the data-classification question, and offers Bedrock as a harness backend.

* Security posture

The VPS holds the Savio key and certificate, the =pass= store with API keys, and the GitHub, rsync.net and Bitbucket credentials.

The instance lives in the =ligon-research= account, reached through IAM Identity Center at Berkeley's portal; the SSO profiles are already in =~ligon/.aws/config= and the account details in =~ligon/Organization/refile_dfly.org=.
SSO credentials are short-lived and minted in a browser, so every AWS API call in this plan runs from the laptop after =aws sso login=; the instance needs no AWS credentials to exist, and the snapshot policy runs inside AWS.
An agent session that works the account logs in itself with =aws sso login --use-device-code= under the =ligon-research-user= profile in its own =~/.aws=, and the human approves the device code in a browser; the human's token files stay private, which the CLI enforces by recreating them =0600= at every login, and the agent never holds the admin role.
If Bedrock is ever wanted as a harness backend it comes through an instance role, never keys on disk; the dispatch execution profile refuses ambient AWS keys and disables instance-metadata discovery for its own reasons ([[file:dispatch-projects.org][dispatch projects]]), so that choice stays confined to sessions run on the VPS.
Account numbers stay out of this note; the repository is public.

- =sshd= with public-key authentication only, password authentication off, reachable over Tailscale or from known addresses with =fail2ban= in front.
- =mosh-server= needs UDP 60000--61000.
- =unattended-upgrades=.
- SuCoder's own separation holds on the box: =coder= cannot read =ligon='s =~/.ssh= or =pass= store, and the only sudo path is the =relay= rule from =config.example.yaml=.
- No laptop secret lives on vantage.
After a first =rsync= of =~/.ssh=, =~/.gnupg= and =~/.password-store= the set was pruned on 2026-10-30, before the first daily snapshot, to what the launcher uses: the BRC certificate key pair minted on vantage itself, which covers every hop including the login nodes and DTN; a vantage-only passphrase-less ed25519 key for rsync.net and Bitbucket, registered there and nowhere else; GitHub over HTTPS through =gh='s credential helper, so no GitHub key exists on the box; a vantage-only passphrase-less GPG key with a =pass= store holding the single entry the config names; and =known_hosts= trimmed to the six hosts in use.
The laptop's seven GPG secret keys, eighteen store entries, the 2009 RSA key that BRC's =authorized_keys= lists, the passphrase-protected =id_ed25519= and the root key for the =hhsurveys= droplet were removed; every one of them is revocable or re-copyable from the laptop, and none is needed because the certificate and the per-service keys do the work.
Passphrase-less is deliberate: =collaborate=, =pull= and the keeper run unattended, the store protects a model-API key and later the BRC PIN, and the laptop's store key has no passphrase either.
The TOTP seed stays in the human's authenticator.
  The keeper asks for an OTP when it needs one and never stores it; the BRC PIN may live in =pass= because it is useless without the second factor.
  Whether a second factor may live on a server the human does not hold is a BRC terms question, not an engineering one; it is open below.
