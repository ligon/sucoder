** Server ownership by mode (outcome 2)

- app-server :: the launched native binary itself holds all eighteen database and sidecar descriptors; the only Unix-socket connections are =/dev/log= and =/var/run/nscd/socket=.
  Nothing under =/tmp/codex-daemon-<uid>= is touched.
- TUI :: the same: the TUI process holds the eighteen descriptors, makes no =codex-daemon= access at all, and connects only to the session bus and its own tmux socket.
  =daemon_auto_start= is "stable, true" in the feature list, but no daemon was spawned for this launch.
- =remote-control --no-daemon= :: the embedded server opened =state_5=, =goals_1=, =queue_1=, =memories_1= and =logs_2= under the override, created a relay socket under =/tmp/codex-rc-<random>/rc.sock= and a control lock plus socket at =/tmp/codex-daemon-<uid>/<64-hex>=, attempted TLS connections to public addresses, and exited 1 with "Remote control is enabled on n0033.savio4 but the connection is errored", because the isolated home has no credentials.
  The 64-hex name differs from the real home's (=75c014f5...= against =1fa531dc...=) and is not the plain SHA-256 of either home path; its derivation was not established.
  The directory is per host, and it was empty after the process exited.

An authenticated remote-control launch cannot be exercised with a synthetic home, and this phase did not use real credentials; what is established is that the embedded server opens its stores under the override before the relay step.

** Shutdown and WAL state

- app-server, stdin closed :: exit 0 within twelve seconds in eight of nine cases, but five of the six main database files stayed at 4096 bytes (=logs_2.sqlite= reached 49152) with all thread content, including the marker, in the =-wal= files.
  The connections were not closed before exit, so nothing was checkpointed.
  A file copy of =*.sqlite= taken after such an exit would be empty; the design's choice of the SQLite backup API, which reads through the WAL, is the correct one, and "sealed" must mean a close that checkpoints, or a backup-API copy, not merely a zero exit.
- app-server, c0 :: stdin EOF did not end the process within twelve seconds because the plugin marketplace =git clone= was still running; SIGINT ended it.
  A graceful-shutdown profile must bound or wait for that sync.
- TUI, =/quit= :: =thread_history_1.sqlite= was closed cleanly (no =-wal= or =-shm= left, marker in the main file) while the other five retained their WAL and shared-memory files.
  Two UI warnings were shown in the pane and were not inspected.

** Lock traffic, the contention mechanism

In c1's six seconds SQLite issued 1656 =fcntl(F_SETLK)= calls on the override directory: 1002 on =state_5.sqlite-shm=, 224 on =thread_history_1.sqlite-shm=, 56--70 on each other =-shm=, and 29 on each main file.
On ext4 these are local; on Lustre each is a lock-server round trip, which is how a nearly idle session becomes "nearly unusable" under contention and how the Oct 1 diagnosis reached 1299 locked warnings in four hours.
No timing claim is made from these uncontended single runs; outcome 7 remains open.

* Consequences for the design

1. The inventory table in the design is confirmed for the six databases on 0.162.1 and should add =agent_message_board_1.sqlite= as flag-gated and optional, and note that no maintenance lock was observed in these modes.
2. The =sessions/= rollout file and, for the TUI, =history.jsonl= are external transcript dependencies in =CODEX_HOME=.
   A generation that captures only the databases does not capture everything the server reads for a thread; outcome 3 must establish whether resume works from the databases alone, or the generation must include the thread's rollout file.
3. The runner must pass an absolute =sqlite_home=: a relative value resolves against the process cwd and lands inside the managed clone.
   It must pre-create the directory with mode 0700 rather than let Codex create it with =0777= masked by umask, and verify effective placement through =/proc/<pid>/fd= as the Oct 1 =cutover.py= did.
   A launch whose location is unusable fails with exit 1 and the error text above; that is the loud failure the design wants, and there is no silent fallback to repair.
4. Precedence is =-c= over =config.toml= over =CODEX_SQLITE_HOME= (cases c3, c4 and c10), as the official reference the design cites states.
   An explicit =-c= from the runner is therefore sufficient, and an environment export alone is defeated by a user's =config.toml= value, exactly as the design predicted; the conflict rule should compare the runner's path against both the environment and the file.
5. "Sealed" needs a definition that checks WAL state: after an app-server stdin EOF the data is entirely in WAL, and after a TUI =/quit= only the history store was checkpointed.
   The backup API reads committed WAL content, so warm captures are unaffected; the sealed profile must either close through a path that checkpoints or accept the backup-API copy as the sealed artifact.
6. In remote-control mode the embedded server creates a per-host control socket and lock under =/tmp/codex-daemon-<uid>/=, and a startup lock in =CODEX_HOME/app-server-control/=; the independent-ownership check must cover both, and an authenticated test is still required.
7. Shared-home plugin and skill synchronization is the dominant non-SQLite I/O and is unaffected by placement; it belongs in the shared-home I/O budget, not the recovery generation.

** Restore and the rollout dependency (outcome 3)

One source server wrote a thread of 6 marker turns under =-c sqlite_home=A=; a warm capture was taken while it ran and a sealed capture after stdin EOF.
Each cell restores one capture into a fresh directory and starts a new server, with the rollout JSONL either left at the absolute path recorded in the database, copied into a fresh home at the =CODEX_HOME=-relative path with the original hidden, or hidden entirely.
Every cell then sends a follow-up turn and records which earlier markers the fake model received.

Findings:

- The rollout file is required and the SQLite history is a projection of it.
  With the file gone from the path stored in =threads.path=, =thread/resume= fails with "no rollout found for thread id", and =thread/read=, =thread/items/list= and =thread/turns/list= fail with "invalid paginated history lineage"; no history reaches the model.
  That holds in the original home as well as a fresh one, and a copy at the =CODEX_HOME=-relative path does not help: the dependency is on the absolute path.
  (The =thread_history_projection_state= table and the =rollout_migration_*= tables in =state_5= say the same thing from the schema side.)
- With the file at its recorded path, a fresh =CODEX_HOME= resumes fully, including a different cwd on =thread/resume= and a follow-up turn whose model request carries the whole earlier conversation.
  Default =thread/list= does not find the thread in a fresh home because it scans =CODEX_HOME/sessions=; =useStateDbOnly= finds it from the restored database.
- Warm and sealed captures restore identically here; the difference between them is not visible through thread history because the server rebuilds the projection from the rollout on resume.
- In the smoke runs the rollout accumulated follow-up turns from earlier cells, and every later cell saw them: a resumed thread shows whatever the rollout holds, not what the restored database holds.

** Abrupt stops and captures (outcome 3, interleavings)

20 seeded runs (base seed 20261015; per-run seed =base * 1000 + i=), each a fresh home and thread of 6 marker turns on =/local=, a warm capture started at a random fraction of a random turn, SIGKILL of the process group at a random fraction of a random later turn, then a post-crash capture from the files the killed process left.
For each capture a fresh server restores it in the same home, with the rollout reset to its post-kill bytes, and the harness records the markers visible through =thread/resume= and =thread/items/list=, whether =thread/turns/list= agrees with =thread/items/list=, a byte search of the captured =thread_history_1.sqlite= and =state_5.sqlite= for markers, and a follow-up turn.
A warm restore passes when every turn whose =turn/completed= preceded the start of the =thread_history= backup is visible and nothing not sent appears; a crash restore passes when nothing not sent appears and the follow-up turn works.

All 20 warm captures and all 20 post-crash captures completed with =quick_check= ok on every database, opened read-only, in 11--24 ms each for 520 KB; all 20 of 20 runs passed both restores, and =thread/turns/list= agreed with =thread/items/list= in every restore.

** Queue and goal replay (outcome 4)

Four variants, each a fresh thread with one turn: a message queued with =codex queue= while the server was stopped; an active goal set with =thread/goal/set=; both; and a goal set active and then =paused= before the stop.
After capture and restore, a fresh server received =thread/resume= and nothing else for 30 seconds.

| Variant | =thread/resume= | Unprompted turns in 30 s | Model requests in 30 s | Requests per second, first five seconds | Queue rows before, after | Goal status after | Requests caused by the next client turn |
|---------+-----------------+--------------------------+------------------------+------------------------------------------+--------------------------+-------------------+-----------------------------------------|
| queue only | ok | 1 | 1 | 1, 0, 0, 0, 0 | 1, 0 | none | 1 |
| goal only | ok | 448 | 447 | 28, 27, 21, 18, 18 | 0, 0 | active | 25 |
| queue and goal | ok | 449 | 449 | 26, 27, 21, 20, 18 | 1, 0 | active | 25 |
| goal paused | ok | 0 | 0 | 0, 0, 0, 0, 0 | 0, 0 | paused | 1 |

Findings:

- A persisted queue entry executes once, unprompted, on =thread/resume=: a =turn/started= and one model request carrying the queued text, and the =queued_items= row is consumed.
- An active goal drives unprompted turns continuously after =thread/resume=: about twenty model requests per second for the whole watch window, each carrying the goal objective, with the goal still =active= afterwards and the next client turn itself producing dozens of requests.
  With the fake model every reply is empty, so the goal loop never sees progress; with a real model each of those requests is paid.
- A goal set to =paused= before the stop produced no unprompted activity at all after resume, and the next client turn produced one request: pausing is a usable hold for goals.
- There is no comparable hold for the queue in the protocol; unattended resume of a thread with queued rows executes them.
  A runner that resumes unattended must therefore either refuse while =queued_items= has rows for the thread, or accept the single execution; it must not resume a thread with an active goal unattended.

** Restart in place and two writers (outcome 5, Codex side)

- Restart in place :: a second server on the same =CODEX_HOME= and =sqlite_home= after a clean stop resumes the thread and the model receives the earlier history.
- Same home, same databases, two servers :: the second =thread/resume= is refused with "thread <id> already has an active writer" (the =thread-writer-locks/<id>.lock= =flock=), and its =turn/start= fails with "thread not found"; the databases stay consistent.
- Different homes, same databases, two servers :: both resume, both complete turns, =quick_check= stays =ok=, and both markers appear in the history afterwards.
  Nothing in Codex prevents two writers when the per-thread lock lives in two different homes; that is the hazard the design's lineage exclusivity exists to prevent, measured.

** Bind mounts: the hot path without Lustre

The human's concern is not Lustre's median latency but its episodes, when every operation takes minutes; the number that matters is therefore how many synchronous Lustre operations a turn contains, not their average cost.
The =bind= sub-test launches the server through =bwrap --unshare-user --uid <own> --gid <own> --bind <local dir> CODEX_HOME/<subdir>=: a per-process mount namespace in which a local directory replaces a subdirectory of the shared home, while every other process keeps seeing the shared home unchanged, the stored rollout path stays =CODEX_HOME/sessions/...=, and Codex's own sandbox still runs nested inside (checked with =codex sandbox=; =/global/scratch= is read-only in it, as outside).
=CODEX_HOME= sat on the Lustre test root, =TMPDIR= on local disk, and strace counted every path touched during six turns after a warm-up, on this slice (job 39969504).
In both bind sets the rollout was physically on local disk, the shared =sessions/= stayed empty from outside, and a second server with the local directories copied to new paths and bound at the same mount points resumed the thread with all seven turns and sent the whole history to the model.

| Bound to local disk                                                  | Lustre operations per turn | What remains on Lustre during a turn                                                                                                      |
|----------------------------------------------------------------------+----------------------------+-------------------------------------------------------------------------------------------------------------------------------------------|
| =sessions=                                                           | about 18                   | =tmp/arg0/<random>/git= (4), =skills/.system/.codex-system-skills.marker= (3), =skills= and =skills/.system= (3), =AGENTS.md= and =AGENTS.override.md= (2), path-component =readlink= and =lstat= calls |
| =sessions=, =.tmp=, =tmp=, =thread-writer-locks=, =shell_snapshots=  | about 10                   | the =skills= stats (6), the two =AGENTS= stats (2), and about one =readlink= per path component of =CODEX_HOME= every few turns              |

All of the remaining operations are metadata calls on entries of =CODEX_HOME= that the turn does not modify; no data is read or written on Lustre during a turn.
They would reach zero by binding a read-only copy of =skills/= and the two =AGENTS= files as well, leaving the path-component lookups, which are client-cache hits unless another client has modified a directory on the chain.
The harness's own artifacts are excluded from these counts: its isolated user home sat on Lustre, so =git= read =~/.gitconfig= there twenty times per turn, whereas production =HOME= is on NFS.
Separately, Codex executes =git= about three times per turn and =lsb_release= every third turn; their PATH walks and =~/.gitconfig= reads touch =/global/home= and =/global/software=, which are NFS, not Lustre.

** Consequences for the design, second set

1. For thread history, the generation does not determine what resumes; the rollout does.
   On resume the server rebuilds the SQLite history projection from the rollout at the absolute path in =threads.path=: without the file every history read fails, and with it a restored database is overridden by whatever the file holds (12 of 20 warm restores showed more turns than their captured database).
   A generation's consistency claim therefore covers goals, queue, memories, logs and the non-history parts of state; for the conversation itself the recovery point is the shared rollout, not the generation.
   The design must choose: either the rollout joins the generation, captured and restored with it, or the history-consistency guarantee is dropped and documented as "whatever the shared rollout contains".
   The first is possible on this build without touching the shared home: the binary has no setting for the sessions directory, but it stores the rollout path as written rather than canonicalized, so a local directory placed at =CODEX_HOME/sessions= keeps the stored path valid; a symlink does it (the =symlink= sub-test) but redirects every process using the home, and a per-process =bwrap= bind mount does it for the managed server alone (the =bind= sub-test above).
   A copy at the =CODEX_HOME=-relative path without either is not found, and rewriting =threads.path= remains the guessed fix the design forbids.
   The trade-off is then measured: with the rollout on local disk and the full bind set a turn contains no Lustre data operation and 1.7 metadata calls, none load-bearing, so a Lustre episode no longer stalls the conversation; a per-turn tail append of the rollout to shared storage costs 13 ms outside Codex's path, is byte-identical at the next =turn/start=, and bounds the crash window to the replication lag rather than a capture interval.
   Rollout skew in either direction does not break resume; the one hazard, a database generation newer than the replica, shows the client turns the model does not remember, so the generation must be captured after the replica is confirmed.
   This record names the choice and does not make it.
2. The rollout is also where the latency is: with the databases local and the home on Lustre a turn took 0.21 s at the median, against 0.51 s with everything on Lustre and 0.042 s with everything on =/local=.
   The design's choice to move only the databases buys part of the improvement; moving =sessions/= as well is possible through the per-process bind mount described in consequence 1, which needs no private home.
3. Unattended continuation must check =goals_1= and =queue_1= before =thread/resume=: refuse or require explicit confirmation when the thread has an =active= goal or queued rows, and offer =paused= as the hold for goals.
   The design's fallback, that unattended recovery of such a profile is unsupported, is the measured outcome for queued work.
4. Lineage exclusivity cannot be delegated to Codex: two homes on one =sqlite_home= are two writers.
   The runner's single-owner rule and its placement check through =/proc/<pid>/fd= remain necessary.
5. Cross-database consistency at a crash remains unmeasured: =state_5= holds only the thread preview, so the byte search of the captures cannot see skew, and the protocol hides it by rebuilding history from the rollout.
   The sealed-only rule for automatic continuation stands until a recovery test covers goals, queue and state rows, which have no rollout to rebuild from.

** Limits

- Fake-model workloads only; no tool calls, approvals, attachments or compaction were exercised, so the inventory of rollout-dependent features is a lower bound.
- The latency arms are one node, one afternoon, two concurrency levels.
- Interleavings cover one writer and 20 seeds.
- Remote control was not exercised beyond the relay step; the TUI's per-prompt residue under =bwrap= is not established; compaction with a real summary is not.

** Next actions

- Implementation (Slice 1 onward) can proceed against these contracts: absolute =sqlite_home=, pre-created 0700, placement verified through =/proc=, rollout recorded in the manifest, goal and queue checks before unattended resume, single owner per lineage.
- Before production opt-in, repeat outcome 4 with a real-model thread once (a paused goal, a queued message) to confirm the hold behavior is not an artifact of empty replies.
- Resolve the rollout choice in consequence 1 before Slice 2 defines what a generation promises; the measured contracts if the bind-mount layout is chosen are: launch through =bwrap= with =sessions=, =.tmp=, =tmp=, =thread-writer-locks=, =shell_snapshots=, =app-server-control=, a read-only =skills/= copy and the =AGENTS= and =history.jsonl= files bound to local disk; replicate the rollout tail after each =turn/completed= with =fsync=, lag-tolerant; capture the database generation only after the replica is confirmed identical; restore as generation plus replica, rebound at the same mount points.
