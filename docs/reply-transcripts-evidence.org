* Summary: what breaks "find the message id, take the next assistant message"

1. The message is not always a =user= entry.
   Claude Code delivers a message typed while it is busy as a =queue-operation= plus an =attachment= of type =queued_command=, not as a =user= entry (LSMS_Library, message 1733).
   Codex injects it into the running turn as a =response_item= with =role: user=, same =turn_id= as the work already under way (CerealDemand, message 8e25).
2. The message text is not at the start of the content.
   A long =send-keys -l= burst reached this Claude session as a paste: the =user= content is the string ="\n\n<pasted_content id=\"935c\">\n[message 00cd ...\n</pasted_content id=\"935c\">\n"=.
   An anchored =^\[message= match fails.
   The paste id is not unique: a later paste into this same session reused =id="935c"=.
3. The id appears in many entries that are not the delivery.
   Claude: =last-prompt= (truncated, ends in U+2026), =api-request-blob= (copies of request content, both roles), =tool_result= entries that echoed it, and the compaction summary (=isCompactSummary: true=).
   Codex: the =event_msg/item_completed= twin of every item, =compacted.payload.replacement_history=, and the copied history of every subagent thread forked after the message (same item =id= as the parent's copy).
   =grep 'message 8e25'= hits 6 of the 8 CerealDemand rollouts; only one is the delivery.
4. The next assistant entry is usually not the reply.
   Claude writes one JSONL entry per content block; after a message come thinking blocks, tool_use blocks and preamble text.
   In this session the first assistant text after 00cd is the bootstrap line ="I'm Sue, running on Claude Opus 5.5. ..."=.
   Codex emits =commentary= messages before tool calls, and the main thread also receives =response_item/agent_message= items from subagents.
5. The reply can come mid-turn and be =commentary=.
   Codex's =REPLY 8e25: ok.= has =phase: "commentary"=, 2 s after delivery, inside a turn that ran from 13:42:59Z to 15:04:38Z.
   Waiting for =task_complete= or filtering on =final_answer= would wait an hour or miss it.
6. The reply may never come, and the summary may say it did.
   LSMS_Library has no assistant entry mentioning 1733 at all, yet its later compaction summary says the relay message was =(answered "REPLY 1733: ok")=.
   If your =--wait= or =peek= did see a =REPLY 1733= on that screen, the transcript is missing something the screen showed, which would be a deeper break.
   If it did not, a mid-turn message can be silently dropped by the model.
7. The reply string also appears in tool inputs.
   Any agent that writes about the protocol (this file, for one) puts =REPLY <id>:= into a =tool_use= input.
   Match only Claude =type: "assistant"= entries with a =text= block, or Codex =response_item= with =payload.type: "message"= and =role: "assistant"=.
8. File order is not timestamp order (Claude).
   The =queued_command= attachment carries the enqueue time (02:55:15.671Z) but is written after a 02:55:50.362Z =tool_result=; its file position marks when the model saw it.
   Use file position for "after" in Claude and =ordinal= in Codex.
9. Finding the file is not solved for compute-node Claude sessions (see section 3).

A matcher that survives all of the above: locate the delivery entry by its harness-specific shape (not by grep), then take the first assistant text item after that position whose text has a line matching =^REPLY <id>:=, with a deadline; report "no reply" rather than falling back to "next assistant message".

* Note: the human's separate-channel suggestion (IRC), 2026-10-23 08:40

The human raised a dedicated channel (IRC, e.g. Ergo) instead of screen or transcript reading.
My assessment, for whoever designs this:
- The facts above argue against making sucoder parse two private, fast-moving transcript formats (both harnesses grew new entry types recently).  Use transcript reading as a diagnostic, not the protocol.
- Any out-of-band channel only fixes the *reply* path, and only if the agent sends its reply through it with a tool call instead of printing it.  That change, not the transport, is what fixes this bug.
- Inbound delivery still needs =send-keys= (or a harness-native channel): idle agents do not poll a socket.
- Claude Code already has a harness-native one, unexplored here: =~/.claude/sessions/4016127.json= has =peerProtocol: 1=, =peerFeatures: ["notify_idle", "reply_across_default_dirs", "artifact_yield"]= and =messagingSocketPath: "/run/user/43292/cc-socks/4016127.sock"=, and n0114 has =/local/job40390255/cc-socks-43292/=.  It is a Unix socket (same host only) and Claude-only; Codex has nothing equivalent that I saw.
- A file mailbox on shared home (the agent runs =sucoder reply <id> "text"=, or writes =~/.sucoder/mail/<id>.reply= itself; the sender polls that path over its existing SSH route) gives the same effect with no daemon, no open port and Unix permissions for auth.
- IRC adds a long-running service (login nodes are a poor host; compute-node addresses change at turnover), a listening port on the cluster network, and an authentication requirement: whatever can post into a channel that feeds agents running with =--dangerously-skip-permissions= can run commands on the cluster.
- No channel helps with message 1733: an agent that ignores a mid-turn message has to be caught by a deadline and a "no reply" result.
