* Tool declarations can be removed

The installed Codex =0.167.1= model metadata selects =tool_mode: code_mode_only= for =gpt-6.1-sol=.
The initial feature switches therefore did not exhaust the mechanisms selecting the model-facing tool surface.
The [[https://learn.chatgpt.com/docs/config-file/config-reference][official configuration reference]] documents a local =model_catalog_json= and nested Code Mode controls; installed schema/help and actual captured requests establish the build-specific behavior below.

The investigator copied the selected model's catalog row and changed these fields, retaining its model slug and other metadata:

#+begin_example
tool_mode: standard
node_repl_disabled: true
experimental_supported_tools: []
apply_patch_tool_type: null
#+end_example

These are changed fields within a complete existing catalog row, not a complete replacement catalog.
The probe combines them with explicit controls for goals, user questions, asynchronous messages, sleep, multi-agent tools, Code Mode and host fallback.
Nested =features.code_mode.enabled=false= and =features.code_mode_host.enabled=false= avoid relying on the earlier boolean-only flags.
=features.code_mode_host.disable_in_process_fallback=true= also disables the fallback host path.
The successful probe removes the old =--disable code_mode= and =--disable code_mode_host= entries and uses these configuration overrides instead:

#+begin_example
features.default_mode_request_user_input = false
tools.experimental_request_user_input.enabled = false
features.send_message_to_user_async = false
features.sleep_tool.enabled = false
features.multi_agent_v2.enabled = false
features.code_mode_only = false
features.code_mode.enabled = false
features.code_mode_host.enabled = false
features.code_mode_host.disable_in_process_fallback = true
features.goals = false
skills.include_instructions = false
#+end_example

The [[https://learn.chatgpt.com/docs/config-schema.json][official configuration schema]] supplies controls not all listed in the prose reference.
The full executable probe and exact control lists remain in the private artifact directory below.

| Probe | Observed native request |
|-------+-------------------------|
| Nested Code Mode/host switches alone | Five original tools remain |
| Additional question/clock/multi-agent controls | exec and wait remain |
| Standard catalog mode, disabled node repl and empty experimental tool list | exec/wait disappear; patch and goal tools remain |

The tool-free captures returned exit code zero without the earlier native startup error.
The parent independently replayed their saved stdout through the existing native trace parser and actual fixture schema validator; both passed.
Against the same-policy nested-disable baseline, the serialized =additional_tools= items shrank from 15,870 bytes to zero.
This is request-byte evidence, not measured token or billing savings; the fixture's usage counters are synthetic constants.
Catalog delivery through an inherited sealed =/proc/self/fd/N= descriptor worked under the existing Landlock filesystem boundary.
This establishes a native tool-omission method without changing provider or model, rather than proving that declarations are harmless.

* Separate cache blockers

The first tool-free pair still injected a skills block containing each invocation's fresh temporary-home path before the first user message.
=skills.include_instructions=false= removed that changing instruction text.
With a sealed catalog and skill instructions disabled, each capture passes the existing prefix validator individually; their paired normalized prefix/settings differ only in =prompt_cache_key=.
Codex supplies a fresh thread-specific key for each invocation.
Disabling Responses Lite did not change that behavior.

The [[https://developers.openai.com/api/docs/guides/prompt-caching][OpenAI caching guide]] distinguishes automatic routing from separate cache-accounting/reuse groups and advises stable keys within a group.
An unchanged instruction prefix alone therefore does not establish useful cross-invocation reuse under these changing keys.
The installed root/exec help and normal/experimental thread-start schemas expose no documented fresh-thread-ID or cache-key selector in the inspected surfaces.
This is a bounded observation about those surfaces, not proof that no native workaround exists.

The investigator also checked the installed =thread/resume= interface.
Its inline history field is explicitly marked unstable and Cloud-only; its path mode does not honor a requested new thread ID, and it has no ephemeral field.
A synthetic zero-turn RPC with a fixed UUID and =history: []= returned error =-32600=, =history must not be empty=, with zero provider requests.
That rejects the proposed strictly empty inline-history seed workaround; no actual conversation was resumed and no nonempty seed was fabricated.
No production use of the unsupported history interface is recommended.

* Workaround assessment

Tool-free requests are a conservative isolation requirement of the current dream profile, not an inherent requirement of provider prompt caching.
Stable tool declarations can be part of a cached prefix.
The [[https://developers.openai.com/api/docs/guides/function-calling#tool-choice][Responses tool-choice API]] also distinguishes declaration from call selection, including =tool_choice: none=.
That API capability does not establish that the native CLI exposes an equivalent control.

Merely permitting the captured declarations in the current certificate is insufficient.
=functions.exec= advertises nested patch, goal and resource operations plus dynamically discoverable tools; it is not established to be inert.
The current trace parser rejects tool events after native capture, which protects publication but cannot undo earlier effects.
Any profile allowing such declarations would need mechanical denial before dispatch, active synthetic attempts against every direct/nested tool, and binding of host configuration and fallback behavior.
Physical omission remains preferable to this larger proof obligation.

A local request-rewriting proxy is not a shortcut: it introduces credential forwarding, HTTP/WebSocket filtering and a second request representation while leaving native dispatch to control.
A direct Responses API adapter could omit tools and control cache boundaries, but would be a separate backend and an explicit authentication/billing choice, not automatic fallback from native credentials.
For immediate operation, the already certified Claude instruction profile or explicitly selected legacy Codex delivery remains available.
