* Construction cases and evidence isolation
:PROPERTIES:
:CUSTOM_ID: construction-cases
:END:

For each repository, prepare three bounded construction runs:

- Initial build :: Admit the first three manifest passages and record all construction work.
- Incremental update :: Add the remaining three passages against the accepted initial generation, with unchanged receipts reused.
  This controlled admission order is an experiment, not a claim that these files were written in that chronological order.
- Targeted repair :: Seed a labeled incorrect memory claim in a disposable copy of the updated wiki, then admit the same frozen evidence with an explicit repair reason.
  SuCoder's wrong claim concerns summary-only success; LSMS's concerns uniqueness proving household grain.
  Record whether correction preserves evidence and necessary unresolved questions.

Record first-build, incremental, and repair costs separately and cumulatively.
Use the exposed questions to improve the construction brief during development, without revealing held-out questions to extractors, verifiers, or consolidation.
Freeze the brief and candidate revision before the independent reader comparison.

An independent evaluator authors six held-out questions per repository from the same source map, with answer rubrics and critical errors, before the construction role receives its admitted bundle.
Include lookup controls, cross-source synthesis, and temporal/scope caveats; archive navigation can ask for a reason already supported by the original evidence, not a fabricated editorial conversation unavailable to the baseline.
Keep held-out files, this protocol, worked examples, and review reports outside every construction mount and model-readable directory.
If that isolation cannot be demonstrated, label the evaluation contaminated and do not use it for a go decision.
Held-out question creation and real model runs are later pilot work; none occurred in this design workshop.

* Reader conditions and measurements
:PROPERTIES:
:CUSTOM_ID: reader-conditions
:END:

Use the same reader harness, pinned model identity, source passages, question, output allowance and evidence-tool interface for all three conditions.
Each answer starts in a fresh session with no inherited earlier answers or private memory.
The reader's tool view exposes only the six immutable source passages and its condition's permitted wiki artifacts.
Its question is supplied separately; answer rubrics, this protocol, worked examples, review reports and other answers remain evaluator-only and outside readable directories.
Verify that boundary with a canary access attempt before scoring; an unenforced or contaminated boundary invalidates the comparison.
Randomize condition order within question and record the seed.

- Baseline :: Maintained documentation and source search over the complete frozen six-passage corpus, with no companion.
- Wiki plus search :: The same evidence tools plus the bounded orientation and updated companion.
- Wiki only diagnostic :: The companion and selected archive entries, with original-source tools disabled; preserve evidence-unavailable qualifications.

Across two repositories, six held-out questions and three conditions give 36 answer attempts for one reader model.
Additional models or repetitions require a separately budgeted extension; do not infer broad model rankings from this small pilot.
Pair the answers by question and report rubric items, critical errors, missed qualifications, evidence actually delivered, archive use, latency, model-native input/output usage and any accounting gaps.
Separate active topic bytes, archived bytes, and raw corpus bytes.
Delivered reader bytes include every orientation, topic, archive and source byte supplied to the model, including repeated retrieval and common instructions under the same counting rule in every condition.
Report common-instruction bytes separately as well, without removing them from the comparison's denominator.
Unique corpus bytes and native input/output token accounting are separate measurements; tool-delivery bytes are not a substitute for the provider's repeated-context billing quantities.
Do not infer consultation from correct answers alone; inspect the tool delivery trace.

Use source/role/time caps from [[file:../dream.org::#reader][the design]] for each construction run, a two-minute reader deadline per attempt, and a two-hour aggregate pilot ceiling.
An operator selects any enforced API-dollar ceiling before the pilot; if the backend cannot enforce that currency bound, it must reject that option and report costs as unknown rather than zero.
A completed source-normalization fixture or a source-only question has no provider cost by itself.

* Decision rule and limits
:PROPERTIES:
:CUSTOM_ID: decision-rule
:END:

These are proposed exploratory thresholds for a later go/no-go, not a statistical power claim.
All source-fidelity, coverage, state/link, privacy-admission, isolation and publication scenario checks must first pass in implementation acceptance.
Stop on a fabricated human ruling, a dropped material survey/command qualification, or an accepted receipt for undelivered evidence.

For a useful wiki-plus-search result, require no critical errors on either repository and no lower total held-out rubric score than the baseline on either repository.
Also require either a gain of at least two rubric items on the synthesis/caveat subset, or at least a 20 percent reduction in median delivered reader bytes with unchanged rubric scores and no increased critical errors.
Report inconclusive or stop when allowances expire, sources cannot be reproduced, or small changes determine the verdict.
The wiki-only condition diagnoses coverage; it is not the default deployment condition.

Compute a break-even query count only when build/maintenance and per-answer savings have compatible measured units and positive savings.
Keep token quantities and unknown currency accounting separate; do not turn an Anthropic benchmark's prices into a prediction for these repositories.
The user evaluates whether the examples explain decisions clearly and whether the companion adds value worth its maintenance.
If maintained-source links suffice, retaining a small orientation with those links is an acceptable outcome.
