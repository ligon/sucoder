* 3. Definitions and conventions

An assignment is a frozen semantic request, identified by its canonical bytes, input digest, role and attempt.
A provider prompt cache reuses computed input-prefix state; it supplies neither a prior result nor evidence of successful execution.
The existing private result cache instead replays a completed validated result without provider startup.
Cache reads, cache writes, uncached input, total input, output and reported currency are separate quantities.
On OpenAI's documented Responses API, input totals include cache reads/writes; on Anthropic's Messages API, =input_tokens= excludes both and total is their sum.
Native CLI usage must be mapped from its verified event format rather than inferred from an API field's spelling.
New provider features require an eligible request boundary as well as identical bytes; a common substring inside a single changing prompt does not establish cache eligibility.

* 4. Invariants

Keep exact source admission, independent review, prior-support preservation, immutable job settings, shared wall-clock/call budgets and compare-and-swap publication.
Keep evidence and wiki text at data priority; they must never become system/developer instructions to gain caching.
Earlier job assignments, traces, usage and receipts retain their old interpretation and replay without inference.
Cache expiry, eviction, unavailable telemetry and a zero hit rate do not authorize another paid request or a model/account/transport switch.
Fresh native isolation remains the default; a retained discovery process or a direct provider API adapter requires a separate reviewed change.
Cache controls and keys are optimization hints, never evidence-admission or access-control mechanisms.

* 5. Reuse decisions

- Reuse :: Existing canonical identity, artifact store, role lock, native confinement, authentication staging, publication and shared wallet.
- Extend :: A versioned request manifest binds the semantic assignment to separate instructions, data blocks, wire bytes and native settings.
  Existing traces bind one canonical stdin blob and cannot describe separate system/user surfaces.
- Extend :: Frozen native capability/build profiles and deterministic prompt rendering; native flags can expose a stable instruction surface without changing evidence authority.
- New :: An explicitly pinned vendor-native Codex launcher for the stable profile, with wrapper-equivalent environment/argv/signals and mandatory native request-capture tests.
  The installed Node wrapper closes extra descriptors; local probes also reject the parent-proc workaround under Landlock, so neither can deliver the sealed schema.
- New :: Sealed memfd schema delivery and bounded inline trusted-policy argv; prelaunch file hashes cannot prevent a native pathname-reopen race.
- New :: A common prompt plan distinguishes trusted policy, untrusted stable data, append-only observations and volatile control data.
  Full user-history caching requires a proven native message/block adapter; field reordering alone is not such an adapter.
- Extend :: Provider-aware usage normalization, missing-field counters and native-versus-estimated cost reporting, leaving old persisted totals unchanged.
- Defer :: API backends, long-lived agent sessions, prewarming, speculative calls and semantic history compaction; none is necessary for the first native-prefix slice.

* 6. Decisions and verification boundary

The reviewed design chooses native-only delivery, an initial instruction-prefix slice for both harnesses, and an explicit gate before claiming caching of untrusted data/history.
This is a scope decision: it gives a feasible first slice without claiming that the present one-prompt transport can cache the expensive accumulated history.
The earlier design task authorized no implementation; the human's subsequent "Okay, let's implement" authorizes the reviewed deterministic implementation slices and native fake-provider certification.
Live paid compatibility/cache-hit probes, live Claude runs and deployment remain separate.
The design and its independent review must state which capabilities remain unverified on the installed builds.
