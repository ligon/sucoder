* Charter

The human requested a goal of implementing robust Codex remote control across different nodes on Savio or elsewhere.
The observed failure is an identity collision, independent of whether the old hostname still has a live session.
The relay rejected this launch with HTTP 409 and =Remote app server already online=, although a pairing code could be issued and claimed.
The phone showed an older host and could not open this conversation.

The implementation covers SuCoder-owned Codex terminal and server-only launches, including the legacy =codex remote-control= spelling, on Linux targets capable of the existing state runner's isolation.
It preserves current conversations and services, uses the existing checkpoint/restore machinery, and gives pairing and status an exact owner to address.
Automatic transfer of a paired identity between allocations, merging independent histories, changing account authentication, and repairing an upstream stale registration are outside this change.
Each new owner receives a fresh identity; this deliberately requires pairing a new launch or renewal successor.
An ordinary reconnect or another client attaching to the running owner keeps its identity.

The human authorized implementation through the active goal while leaving the session.
The scope above applies that authorization; no additional design approval is required before reversible implementation and testing.
Existing live processes, account-wide state, and allocation ownership remain protected.

** Definition of done

1. Concurrent owners starting from the same shared Codex home have distinct installation and enrollment identities, including after restored state.
2. Neither startup, shutdown nor failure modifies the shared installation ID, shared enrollment database, another owner's runtime, or a source generation.
3. Remote-control launches use private databases and transcripts with the existing durable checkpoints, including when no local-tier working clone is configured.
4. Legacy service launches and terminal/server modes all use an owned foreground app-server; signals stop only the owned processes.
5. Status distinguishes local process/socket readiness from relay connectivity, and pairing targets the selected live owner and checks its returned environment.
6. Missing isolation support, disconnected relay, stale metadata and unsupported protocol behavior produce actionable failures without silently switching to a shared daemon or allocating work.
7. Existing restore, renewal, explicit history selection, model/policy settings and context behavior pass their targeted regressions; new behaviors have meaningful tests and the Python suite is run.
8. A reproducible live probe shows simultaneous isolated relay connections where account/backend access permits; Android discovery and conversation opening are recorded separately when the human returns.

* Design

** Identity and enrollment

Generate one UUID for a new remote server owner and write it to a private installation file in that run's local state.
Bind the file over the existing =CODEX_HOME/installation_id= only inside the owned process namespace.
Keep the public and canonical home path unchanged.
Do not copy or rewrite the shared installation file, and do not include the generated identity in conversation restoration.

Before Codex opens a restored or reused private database with this new identity, remove only its =remote_control_enrollments= cache.
Run this operation after state ownership and restore checks, before any pre-launch helper or real server can enable remote control.
Never edit a source checkpoint or the shared database.
Unknown incompatible cache schemas refuse remote startup instead of guessing.
Suppress remote-control preference resolution in the one-shot helper used to repair restored working directories.

** Placement outside local-tier clones

Every remote-control launch uses the existing state runner.
With configured local-tier placement, keep the existing allocation-local root and restore/renewal behavior.
Otherwise the runner creates its own private node-local temporary root without moving the working tree.
The root remains available after exit; final-checkpoint failure must not delete the only unsynced state.
Database generations and transcript replicas use the same durable root and format as existing managed state.

Publish the actual run path in pane metadata when startup has established it.
Status and drain can then locate a generic run without inventing a =job<ID>= path.
A reconnect to the existing tmux launch reuses that server and its metadata.
An explicit managed-state opt-out cannot authorize a remote launch against shared state; report the conflict and how to resolve it.
Unsupported isolation environments fail clearly, while ordinary remote-disabled Codex behavior stays intact.

** Owned transport and control

Normalize both remote-control flag modes and the legacy service spelling to an owned foreground app-server and optional terminal client.
Keep the same private Unix WebSocket socket for local terminal and control requests.
Persist a private receipt containing run/scope, actual host, installation UUID, socket, helper path and process incarnation.
The receipt has no credential or pairing secret.
Use the existing in-allocation route for confined requests and reject stale or mismatched process/node identities.

The control helper uses a bounded stdlib-only WebSocket client and only diagnostic/pairing RPCs.
It does not resume a thread, start inference, start a daemon, or modify another registration.
Pairing first requires relay status =connected= and the expected installation ID, then checks the pairing response's environment against that status.
A claimed code and a listening local socket are never advertised as proof of remote reachability.

Expose explicit status and pairing commands for the selected mirror/target.
Print enough owner information to distinguish two services whose upstream display label is the same physical hostname.
Terminal QR rendering belongs on the launcher; the compute node needs no image package or X11.
Never write pairing secrets to persistent launch records or ordinary logs.

** Failure and renewal

Leave transient relay reconnects and token refresh to Codex while retaining the same owner identity.
Report degraded remote access without destroying a usable terminal conversation.
Do not rotate identities on each failed connection and do not stop a suspected old node automatically.

A replacement server gets a new identity even when it restores the predecessor's conversations.
The existing acknowledged-drain and sealed-generation rules still govern conversation continuity.
Thus an overlapping predecessor, a delayed relay disconnect or a stale registration cannot claim the replacement's identity.
Preserving pairing across replacement would require a separate durable identity-transfer and fencing design.
